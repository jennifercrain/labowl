Programming Labs

Guide students through debugging while they work on coding labs and assignments.

Why Programming Labs Matter

In many courses, our traditional study strategies work well to help students organize ideas and process information. Programming can feel different. When a student is working in zyBooks or another coding environment, the immediate challenge is often figuring out what to do when their code behaves differently than they expected.

The student is already in the middle of the task. They’re running code, interpreting results, and trying to understand what went wrong. Debugging is a real-time thinking process.

When Something Breaks

When something breaks, students may react quickly and lose track of what each test tells them. You might see a student:

  • Change several things at once.
  • Run the program again without predicting what will happen.
  • Skip reading the full error message.
  • Lose track of what they’ve already tested.

These are signs the student may need a more deliberate debugging process.

Programming Labs give Peer Navigators a structured way to guide a student’s thinking while they work through coding labs or assignments.

These sessions emphasize debugging literacy, the ability to observe what code is doing, test ideas deliberately, and use the results to decide what to try next.

Two Approaches to Helping Students

See the difference between traditional tutoring and programming coaching.

The Scenario

A student is working on a Python lab. Their code runs but produces the wrong output. They've been staring at it for 20 minutes and just changed three things at once without knowing which one might fix it.

Traditional Tutoring

Focus: Teaching the content

  1. S

    Student: "What's the problem with my code?"

  2. T

    Tutor: "It's not giving the right answer."

  3. S

    Student: "My loop is wrong, right?"

  4. T

    Tutor: "Use range(len(list)) here and += on line 12."

  5. S

    Student: "Okay, got it."

The Result

Code works, but the student didn't learn why it was broken or how to find similar issues next time.

Programming Coaching

Focus: Building thinking process

  1. S

    Student: "Before I change anything, what should my code do?"

  2. P

    Peer Navigator: "Good question! What do you expect it to do?"

  3. S

    Student: "Add up all the numbers in the list."

  4. P

    Peer Navigator: "And what's it actually doing instead?"

  5. S

    Student: "Only giving me the last number."

  6. P

    Peer Navigator: "Walk me through what happens each loop iteration—focus on the total variable."

  7. S

    Student: "Oh! I'm using = instead of +=. It overwrites instead of adding!"

The Result

Student discovered the bug themselves and built a mental model for finding similar issues independently.

The Key Difference

Debugging literacy isn't about teaching Python—it's about teaching students to slow down, form hypotheses, and test systematically. The goal is to build a thinking process they can use every time something breaks.

The Role of the Peer Navigator

Programming Labs follow the philosophy of peer coaching. Help the student slow down, observe what’s happening, and think through the problem step by step. Keep the student thinking, even when you spot a potential fix right away.

Guide the Student’s Thinking

  • Clarify the problem.
  • Interpret what they’re seeing.
  • Test ideas intentionally.
  • Reflect on what worked.

Leave the code and decisions in the student’s hands. Teaching programming concepts, correcting syntax, rewriting code, and providing direct solutions fall outside the Peer Navigator role.

The Lab Owl Framework

Lab Owl is the coaching framework Peer Navigators use to guide debugging conversations during Programming Labs. When students feel overwhelmed or unsure where to start, the framework gives the conversation a clear direction and helps the student decide what to test next.

Lab Owl Helps Students

  • Identify where a problem begins.
  • Observe what their program is doing.
  • Isolate one variable at a time to test.
  • Recognize patterns in outputs.
  • Build independent debugging habits.
